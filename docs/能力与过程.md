## 一、Tool 与 Capability

## 1.1 定义

**Tool = Capability（能力）**：Agent **能调用什么**，以 LLM tool schema 中的可执行项呈现。

| 概念 | 层 | 运行时 |
| --- | --- | --- |
| **Tool** | 能力 | `web_search`、`read_file`、`mcp_github_create_issue` 等；由 `check_fn` / env 决定是否注册 |
| **Skill** | 过程 | `SKILL.md` 指令；教 agent **如何组合** Tool；**不**向 schema 注册新 Tool |

**Normative**：

- 「有没有 `web_search`」→ **Tool**；「先搜再写 digest」→ **Skill / SOUL**。
- 禁止 Skill 内 curl/脚本 **替代** 已声明 Tool（reader 反模式）。

## 1.2 Tool 的三种来源（同一套 Capability 模型）

运行时无差别——均为 toolset + schema 工具名；区别在 **catalog 归属与规划视角**：

| 来源 | 说明 | 典型名 |
| --- | --- | --- |
| **系统内置 Tool** | Hermes 自带；catalog 真源 `CONFIGURABLE_TOOLSETS` | `web`, `file`, `terminal`, … |
| **Domain Tool** | 某 domain **规划并选用** 的能力集合（内置子集 ± MCP） | reader：`web` + `file` + `skills` |
| **MCP Tool** | 外部 server；`mcp_servers.<name>` | 运行时 `mcp-<name>` |

**Domain Tool 不是新 runtime 类型**；「Domain」= 业务规划视角（见第三部分）。

## 1.3 Hermes 机制与三分工

| 机制 | 作用 |
| --- | --- |
| `toolsets` + `platform_toolsets.<platform>` | 启用哪些 toolset |
| `web.backend` 等 | 内置 Tool 的 provider |
| `mcp_servers` | MCP 连接与 env |
| `profiles/master/.env` → child | secrets；`check_fn` 是否通过 |
| `registry.check_fn` | Tool 是否进 schema |

**Normative · 与 Master 分工**（[Agent定义模型 §2.3.1](./Agent定义模型.md#231-三类能力必分)）：

- **Domain Tool** 配置在 **业务 slug** 的 Git overlay / profile；**不在** `profiles/master/`（Master 只管编排：plan / 建卡 / dispatch）。
- 机检 BD-12 / BD-12b 见 [规范附录 B](./专业智能体规范.md#附录-b-labspecvalidate-checks-枚举)。

**Note**：overlay 常含 composite **`hermes-cli`**（Hermes 默认工具束）；domain 能力在 **`platform_toolsets.<platform>`** 中 **额外** 列出 `web`、`file` 等（见 §3.5 示例），勿与「只有 hermes-cli」的 scaffold 默认混淆。

## 二、智能体消费 Tool

> **本节边界**：描述 **单个 slug** 如何消费 Tool（列表 / 选择 / 配置）。  
> **不**描述 domain 能力从哪来——那是 **第三部分**；本节只假设 catalog 与 domain 规划表已存在（附录 C）。  
> **一期落地规格**：[能力与过程(一期).md](./能力与过程(一期).md)（Lab + Production · T1 + UI）。

## 2.1 列表（List）

**含义**：对该 slug 展示 **相关 Tool 能力及就绪状态**（一条合并视图，不分「系统列 / domain 列」）。

**四层漏斗**（列表 UI / API 应对齐此模型）：

```text
① 平台 Catalog（审批人维护 · 附录 C）
        ↓ 允许选用
② Domain 规划（第三部分 · 该 slug/domain 需要什么）
        ↓ 交集
③ 已选（overlay · toolsets / mcp_servers）
        ↓ env + provider
④ 就绪（readiness · schema 是否注册）
```

| 漏斗层 | 数据来源 | 状态 |
| --- | --- | --- |
| ① Catalog | `CONFIGURABLE_TOOLSETS` + 附录 C 登记 MCP | **现网**（内置）；MCP catalog **规划** |
| ② Domain 规划 | CHARTER / 规划表；BD-12 **推断集** | **现网**（BD-12） |
| ③ 已选 | `config.overlay.md` + `config.production.overlay.md` | **现网** |
| ④ 就绪 | `runtime/readiness` | **现网**（Lab · T0：`env.toolset.*` / `mcp.*.env`）；`runtime.registered.*` schema 细检 **规划**（T1） |

**列表每项展示**：toolset 或 `mcp-<server>` 名、provider、依赖 env、configured / readiness / 是否进 schema。

**Normative · 漏斗 ② 机器可读真源（T1 前钉死）**：

| 用途 | T1 前真源 | T3+ |
| --- | --- | --- |
| API `funnel.planned` | **BD-12 推断集**（`lab.spec.validate` 同款逻辑） | 可选叠加 §3.1 规划表 diff |
| 产品/domain 对齐 | §3.1 **规划表**（文档 + 评审；**非** Git 字段） | 可结构化进 CHARTER / agent.model |

**Normative**：T1 前 implementer **不得**自造第三套「planned」来源；UI 展示 human 规划表时可与 BD-12 推断 **并列 diff**，但机检与 API 以 BD-12 为准。

**Normative · 规划表 vs 推断集**（漏斗 ② 与 BD-12）：

| 真源 | 用途 | 谁维护 |
| --- | --- | --- |
| **Domain 规划表**（§3.1） | 产品：该 domain **应该** 要什么能力 | 产品 + Builder 共定 |
| **BD-12 推断集** | 机检：SOUL/CHARTER **文案** 推断应启用哪些 toolset | `lab.spec.validate` 自动 |

二者 **须一致**：规划表 P0 toolset ⊆ overlay，且 SOUL/CHARTER 须出现对应能力表述，否则 BD-12 报 `overlay missing toolsets: …` 或 overlay 与推断不符。`lab_version_save` → `ensure_impl_bundle` **负责收敛** overlay 与推断集（**现网**）。

## 2.2 选择（Select）

**含义**：把 Tool **启用** 写入 slug 的 Git overlay（不改 Hermes 源码）。

| 操作 | 落盘 | 状态 |
| --- | --- | --- |
| 启用 toolset | `config.overlay.md` → `toolsets` + `platform_toolsets.skstudio` | **现网** |
| 同步 Production domain 段 | `config.production.overlay.md` → `platform_toolsets.cli` | **现网**（BD-12b） |
| 启用 MCP | overlay 引用 **附录 C 已登记** server | **规划**（catalog 门禁 UI） |

**Normative**：`lab_version_save` → `ensure_impl_bundle` **唯一**写 overlay；禁止 `files_json` 手改。

**机检**：BD-12、BD-12b（**现网** · blocking spec-ready）。

## 2.3 配置（Configure）

**含义**：为 **已选** Tool 设 provider / secrets，使 runtime 注册进 schema。

| 配置层 | 内容 | 谁可改 | 状态 |
| --- | --- | --- | --- |
| Provider | `web.backend: firecrawl` 等 | Builder · overlay | **现网** |
| Secrets | `*_API_KEY` 等 | **`SKSTUDIO_GROUP_CREATION_REVIEWERS`** → `profiles/master/.env` | **现网** |
| MCP 基线 | `mcp_servers.*` 模板 | **审批人**（附录 C） | **规划** UI |
| Profile 继承 · tool env | master → child `.env`（**按 config 推导**，非全量 `*_API_KEY`） | `sync-runtime` / promote ensure | **现网**（T0 · Lab + promote ensure） |
| Profile 继承 · 推理 env | master → child `.env`（model provider `*_API_KEY`） | `ensure_inference_from_master` | **现网**（与 T0 **双轨并存** · 见附录 G.1） |

**Normative · sync-runtime**：写 profile `.env` 后若 Gateway 已在跑，须 `restart_gateway: true`，否则新 key 不进进程 env（[§3.3 · L1 操作顺序](#l1-操作顺序lab--normative)）。

**Normative**：普通用户 **不得** 改 master secrets 或私挂 MCP。审批人名单 = `SKSTUDIO_GROUP_CREATION_REVIEWERS`（与建群/发布共用，[建群审批](./skstudio-建群审批-需求与设计.md)）。

## 三、Domain Tool 全生命周期

> **本节边界**：**为一个 business domain 供给 Tool 能力** 的五阶段 checklist。  
> **slug 上的列表/选择/配置操作** → 一律按 **第二部分**；本章只多给：规划表、实现路径、测评 runbook、部署分工、overlay 示例。

## 推荐时间线（normative · 按依赖排序）

五节标题是 **checklist 维度**，不是严格时间顺序。实际操作请按下列流水线：

```text
3.1 规划（规划表 + CHARTER 能力表述）
    ↓
3.2 实现（catalog 可用 · 审批人 master env）
    ↓
3.5 配置落盘（lab_version_save → ensure_impl_bundle · 双 overlay）  ← 紧接实现
    ↓
3.4 部署（materialize · sync-runtime / promote · profile 生效）
    ↓
3.3 测评（L1 readiness → L2 SCENARIOS / REG-K01）
```

**勿**在 overlay 未落盘或 L1 未过前跑 REG-01（见 §3.3）。

```text
规划 → 实现 → 配置落盘 → 部署 → 测评
         ↑ 第二部分 List/Select/Configure 在此生效
```

## 3.1 规划

**目标**：列出 domain **必须具备** 的 Tool 能力（规划表），与 CHARTER / BD-12 推断集一致。

**步骤**：

1. 从 CHARTER INTAKE·DELIVERABLE 列 **domain 动作**。
2. 映射 **toolset / MCP**（下表）。
3. 标 provider、master env；绑 REG-01 / REG-K01。
4. 写入 CHARTER（产品语言）；机检以 overlay 为准。

**动作 → Tool 映射**：

| Domain 动作 | toolset / MCP | provider / env |
| --- | --- | --- |
| 网页搜索 / 抓正文 | `web` | firecrawl + `FIRECRAWL_API_KEY` |
| 写 workspace 交付物 | `file` | — |
| 内部知识库 | `mcp-<server>` | 附录 C 登记 + token |
| 查 skill 文档 | `skills` | — |

**规划表模板**：

| Domain 能力 | toolset | provider | 必需 env | Lab | Kanban |
| --- | --- | --- | --- | --- | --- |
| 取网页/搜索 | `web` | firecrawl | `FIRECRAWL_API_KEY` | REG-01 | REG-K01 |
| 写 digest | `file` | — | — | REG-01 | REG-K01 |

**完成标准**：P0 均有 toolset；推断集覆盖；可进入 §3.2。

## 3.2 实现

**目标**：规划表中的 Capability 在 **平台 catalog** 上可用（尚不要求场景 sidecar pass）。

| 路径 | 何时 | 谁 | 状态 |
| --- | --- | --- | --- |
| 选用内置 toolset | 默认 | Builder + 审批人补 master env | **现网** |
| 登记 MCP | 需外部 API | **审批人** · 附录 C · **或** [二期 Forge](./能力与过程(二期).md) 本机 integrator（单人 MVP） | **规划** |
| Hermes plugin | 多 domain 复用 | 上游 PR + 审批人加 catalog | **现网**（机制）· 登记 **规划** |

Domain Tool **不在 slug Git 写 Python**（除非 Hermes 上游缺陷）。

**实现完成标准**（路径二选一）：

- [ ] **Catalog 路径**：P0 行有 toolset/MCP；BD-12 / BD-12b 可绿；master `.env` 含必需 key；MCP 已在附录 C 登记（若有）
- [ ] **Forge 路径**（[二期 §1.2](./能力与过程(二期).md#12-对齐-能力与过程-3)）：`mcp-forge/<name>/` Done + integrator I1–I5；slug overlay **可选**（一期消费侧）

## 3.3 测评

**目标**：Tool **就绪** + **SCENARIOS 可验收**。

### 两层（不可混谈）

| 层 | 测什么 | 通过意味 | 状态 |
| --- | --- | --- | --- |
| **L1 · Tool 就绪** | env、provider、schema 含关键 tool 名 | 能力 **在不在** | env：`env.toolset.*` **现网**（Lab · T0）；schema：`runtime.registered.*` **规划**（T1） |
| **L2 · Domain 场景** | REG-01 / REG-K01 + sidecar | 能力 **能否交付** | **现网** |

### L1 操作顺序（Lab · normative）

1. 审批人确认 `profiles/master/.env` 含规划表 env。  
2. `POST .../profile/sync-runtime` `{ "restart_gateway": true }`（**现网**）。  
3. `GET .../runtime/readiness` → `ok: true`（**现网**）。  
4. （可选）`hermes -p lab-<slug> gateway status` 为 running。  
5. **T1 前过渡**：readiness **已**含 `env.toolset.*`（T0）；**尚不**含 schema 注册细检（`runtime.registered.*`）时，L1 须 **人工确认** 对话工具列表含规划表关键 tool（如 `web_search`）。**禁止**仅凭 BD-12 绿即认为 L1 过。  
6. **此后** 才 `@专家 Bot /new` 跑 SCENARIOS（[九期 §5.4](./hermes与skstudio集成(九期).md)）。

### L2 与门禁

| 验证 | 环境 | 门禁 | 状态 |
| --- | --- | --- | --- |
| BD-12 / BD-12b | Git overlay | spec-ready | **现网** |
| readiness | lab profile | materialize 后 | **现网** |
| REG-01 sidecar `1/1_pass` | Lab IM | Lab Done · PUB-1 | **现网** |
| PUB-4b | Git | publish-preflight | **现网** |
| REG-K01 | Kanban worker | HD-7b 人检 | **现网** |

### 失败归因

| 现象 | 优先查 | 归部分 |
| --- | --- | --- |
| 无 `web_search` | Lab：profile `.env`；未 sync-runtime + restart | L1 · §2.3 |
| readiness 绿但 IM 无 tool | Gateway 未 restart；或 schema 未注册（T1 前人工查） | L1 · §3.3 step 5 |
| readiness 绿但场景 fail | SOUL/Skill 过程 · fixtures | L2 · Skill |
| Lab 绿 · worker block | production overlay；**production `.env` 未 sync** | BD-12b · §3.4 · **一期** `production/sync-runtime` + `pub.tool.*` |
| MCP 工具不可用 | 附录 C 未登记；token 不在 master | §3.2 · 附录 C |

## 3.4 部署

**目标**：secrets + merged config **到达 runtime profile**（第二部分 Configure 的 **环境侧**）。

| 步骤 | Lab | Production | 状态 |
| --- | --- | --- | --- |
| secrets 真源 | `profiles/master/.env` | 同左 | **现网** |
| 继承 child `.env` | sync-runtime / ensure | promote ensure + **一期** production sync / validate | **现网** ensure / **一期** validate |
| profile 目录 | `profiles/lab-<slug>/` | `profiles/<slug>/` | **现网** |
| 启动 | `gateway/start` | dispatch spawn | **现网** |

## 3.5 配置落盘
